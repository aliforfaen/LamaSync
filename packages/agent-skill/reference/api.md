# REST + WebSocket API reference

The `lamasync` CLI (see `reference/cli.md`) is local-first: it drives the
local daemon, reports host health, and registers the device. Fleet
management — folders, backends, app protections, mobile devices, shares,
operations — is the **web UI + this REST API**; there is no fleet CLI
surface. Use this reference when you operate or debug the API directly.

**Always prefer fetching the live OpenAPI 3 spec** at
`GET /swagger/json` for exact request/response field names when writing
write calls. The web UI and Swagger UI consume the server contract, so what
`/swagger/json` says is what the server actually enforces.

> "Don't trust this document for schema details — trust /swagger/json."
> If this file disagrees with the live spec, the live spec wins, and the
> drift-check should be reporting the gap. File it.

## Auth

Auth is a single `Authorization: Bearer <key>` header on every request —
**except** three deliberate pre-auth routes (see below) and the mobile
web-session cookie path (see below). The header, when present, is
authoritative: a malformed or unknown credential is a 401 and never falls
back to the cookie.

Four bearer credential kinds (LAMA-234):

| Kind      | What it is | Scope |
|-----------|------------|-------|
| `master`  | The `LAMASYNC_API_KEY` env value on the server. Never stored in SQLite, never returned by any route, never shown in the UI. | Full super-admin surface. Existing clients keep working until re-paired. |
| `admin`   | A managed key created via `POST /api-keys` (or the Web UI). Secret shown once at creation; revealable later only via explicit `POST /api-keys/:id/reveal`. | Full admin surface incl. managing other managed keys. |
| `device`  | Minted by the pairing exchange, bound to exactly one host. | Only that host's daemon calls — config, registration, heartbeat/reports, claiming and completing its action queue (never enqueueing), locks, conflicts, restic snapshots + restore jobs, its own app protections + their snapshots (list/get/download/upload), release checks, `/auth/me`. Assignment PATCH is limited to that host's `mode` field. Templates are admin-only. |
| `deploy`  | Managed key (LAMA-301) created via `POST /api-keys` with `kind: "deploy"`, held by the LXC-resident deploy agent. | Only the server-deploy agent routes — peek/claim/progress/complete deploy jobs. Cannot request or read jobs, cannot touch anything else. |

- `401 Unauthorized`: missing, wrong, or revoked key — a device that was revoked gets 401 exactly like a bad key.
- `403 Forbidden`: the key is valid but lacks authority for the route (device key hitting an admin route, or a device key touching another host's rows).
- Identify the active credential with `GET /auth/me` (bearer mode for all four kinds above, session mode for cookie web sessions). Mobile NATIVE tokens are confined to `/mobile/*` and never reach `/auth/me` (403) — see the Mobile table rows.
- Managed key secrets are encrypted at rest (AES-256-GCM); lists and normal reads return masked metadata only.

### Pre-auth routes (no bearer/cookie required)

Three operations are deliberately **auth-exempt** (exact method+path in
`server/src/auth.ts` `AUTH_EXEMPT_ROUTES`): the caller cannot yet hold a
credential, and the route re-checks state itself:

- `POST /pairing/:code/exchange` — the single-use pairing code is the proof of intent.
- `POST /mobile/enrollments/:id/exchange` — the enrollment id + one-time QR secret are the proof of intent.
- `POST /mobile/web-session` — the web grant in the body is the proof of intent (a bearer is a valid-but-wrong authority → 403).

They are marked `security: []` in `/swagger/json`, and the OpenAPI spec's
global bearer security does not apply to them.

### Mobile web-session cookies (LAMA-296)

The Android companion may bootstrap a **cookie web session** from its web
grant and open the SPA in a WebView without a second login. The
`__Host-lamasync-mobile` cookie (Secure; HttpOnly; SameSite=Strict; 12 h)
is accepted **only when no `Authorization` header is present at all** — any
explicit header, even malformed or empty, is a 401 and never falls back to
the cookie. Cookie-authenticated mutations additionally require the exact
trusted Origin and the session CSRF token (`X-CSRF-Token`), so the web
grant path is never a bearer bypass.

## Base URL

The server listens on a configurable port (default `8080`). On the
tailnet-deployed production instance:

```
http://<lamasync-server-tailnet-ip>:8080
```

For local dev: `http://127.0.0.1:8080`.

## WebSocket auth (LAMA-118)

The `Sec-WebSocket-Protocol` header carries auth. The server accepts three
encodings of the API key in the second subprotocol slot:

1. the raw key
2. base64
3. unpadded base64url (RFC 6455 forbids `=` padding in a subprotocol token)

```js
const token = btoa(LAMASYNC_API_KEY)
  .replace(/\+/g, "-")
  .replace(/\//g, "_")
  .replace(/=+$/, "");
const ws = new WebSocket(
  "ws://<lamasync-server-tailnet-ip>:8080/api/v1/ws",
  ["lamasync-auth", token],
);
ws.onmessage = (e) => console.log(JSON.parse(e.data));
```

Events: `operation`, `host`, `host_renamed`, `lock`, `mount`, `conflict`,
`restic_snapshot`, `restic_restore`, `action`, `browse_job`,
`server_deploy` (LAMA-301), `sync_progress` (LAMA-327). Their shapes
live in the OpenAPI 3 spec at `/swagger/json` under `WSEvent`.

## Schemas

For exact request/response shapes and field nullability, prefer the live
spec. The high-level shapes (verbose commentary):

- `Host { id, hostname, tailnetIp?, lanIp?, lastSeen?, status, version?, updateAvailable?, updateStatus?, configRevision?, os?, storageUsedBytes?, hostClass? }` — `hostClass` (LAMA-298) is seeded by daemon detection on the first heartbeat (`server/desktop/laptop/nas/phone/tablet/unknown`) and stays fixed after the operator sets it via `PATCH /hosts/:hostId/class`. It drives per-class web-ui icons and offline-notification routing: `host_offline` is an alert only for always-on classes (`server`/`nas`); laptops/phones/tablets are expected to sleep, so their offline edge is suppressed. The fleet's "needs attention"/degraded verdict likewise only counts always-on hosts.
- LAMA-345 (evidence-based update verdict). `updateStatus { kind, reason, label, currentVersion, releaseVersion, releasePublishedAt, actionable }` is derived in ONE place (`@lamasync/core/fleet-health`, serialized by `packages/server/src/fleet-health.ts`) and shared by `/health`, `/hosts`, `GET /hosts/:hostId`, the notification sweep and the web UI. `kind` is `current | available | not_evaluated | unknown`; `updateAvailable` on the wire is exactly `kind === "available"`, so the boolean can never claim more than the evidence supports. An "update available" claim requires the device to have checked in **at or after** the release's `publishedAt` (the boundary is inclusive, from the cached `release-cache` value). A device whose `lastSeen` predates the release is `not_evaluated` / `checked_before_release` with the label "Update not evaluated — this device has not been heard from since before <version> was released"; a device that has never reported is `not_evaluated` / `never_seen`; a missing or unreadable release time refuses to guess. A device running a NEWER build than the published release is `current`, not nagged.
- LAMA-345 (fleet summary). `HealthResponse.fleetHealth` aggregates device state and managed-folder health into four buckets, each `{ total, items, truncated }` with a bounded item list (worst first) and a plain-language `headline`, plus `healthy { folders, hosts }`, `updatesActionable` and `updatesNotEvaluated`:
  - `needsIntervention` — the ONLY red bucket: folder states `unsafe | resync_required | blocked`, or an always-on machine (`server`/`nas`) that is offline/degraded.
  - `checkWhenOnline` — yellow/info: folders awaiting a run or a device (`new_host`, `recoverable`), folders whose device is offline, devices that sleep by design (`laptop`/`phone`/`tablet`/`desktop`/`unknown`), and actionable updates.
  - `healthy` — counts only; a usable sync record with a clean last run, and online devices.
  - `unknownOrStale` — never reported, or a report older than the shared 15-minute budget. Deliberately distinct from unhealthy: "not heard from" is not "broken".
  Each item carries `kind` (`folder | host | update`), a `title`, a plain-language `detail`, a `tone`, an `href` (`/folders?folder=<id>&host=<id>` or `/hosts/<id>`) and the health-card `action` when one applies. A host already in `needsIntervention` suppresses its own folder items so one root cause is not counted twice.
- `Folder { id, name, type, createdAt?, encrypted?, cryptPassword?, backend?, backendId?, s3Bucket?, gitProvider?, gitRemote? }`
- `FolderAssignment { id, folderId, hostId, role, localPath, remoteName?, destination?, syncExpr?, enabled, conflictStrategy?, preSyncCmd?, postSyncCmd?, ignorePath?, mountIgnorePath?, timeoutSec?, bandwidthSchedule?, maxRetries?, availableSpaceThreshold?, cacheProfile?, cacheMaxSize?, resticRepository?, resticPassword?, watchEnabled?, watchQuietSec?, ignoreGitMetadata?, respectGitignore?, bisyncMaxDeletePercent?, mountCacheMode? }` — (LAMA-302 watch fields, only honored for effective `sync` assignments and all default-off: `watchEnabled`, `watchQuietSec` (`null` => 30 s, validated 10-300), `ignoreGitMetadata`, `respectGitignore`.) `syncExpr` is validated on write with the daemon's own scheduler grammar (5-field cron or a supported `@`-keyword); a non-empty value the daemon could not arm is a 400, `null`/empty means no schedule (LAMA-336). `destination` (LAMA-294) is the explicit relative path/prefix on the remote, separate from the connection alias `remoteName`; `null`/omitted uses the default. Ordinary backups host-scope by default to `<folder-name>/<host-id>`; sync/mount stay shared (`<folder-name>`). The canonical destination key is the server-side lock identity. **LAMA-345 allowlisted tuning** (typed, validated; there is no free-form rclone arguments or configuration field anywhere): `bisyncMaxDeletePercent` (`null` or an integer 0-100 — rclone bisync `--max-delete`, a PERCENTAGE of a side's files; `null` means rclone's own default, currently **50%**, and never "no cap") and `mountCacheMode` (`null | off | minimal | writes | full`, rclone `--vfs-cache-mode`; this reaches the persistent mount and its restarts, not just a one-shot command).
- LAMA-345 managed-folder health contract (shared by daemon, server and web UI, exported from `@lamasync/core/folder-health`):
  - `FolderHealthState` — `healthy | new_host | resync_required | recoverable | unsafe | blocked | busy | unknown`, assignment-level (the same folder can be healthy on one device and unseeded on another).
  - `FolderHealthReport { hostId, folderId, assignmentId?, state, reasons, facts, reportedAt }` — the daemon→server body of `POST /folder-health`. `reasons` is a bounded list of `{ code, message, remediation, action }` where `action` is one of `diagnose | plan | sync | initialize | seed | resync | resume | cancel`.
  - `FolderHealthFacts { folderType, effectiveType, enabled, paused, runInProgress, rcloneAvailable, localDir, freeSpaceBytes, freeSpaceThresholdBytes, watcher, filter, baseline, activePhase, pendingConflicts, lastRun, measurement }` — lightweight facts only. `localDir` is `ok | missing | not_directory | unreadable | unwritable`; `baseline.present` requires a matching `*.path1.lst` + `*.path2.lst` pair and `baseline.ready` additionally requires no `.lst-err` and no in-flight `.lst-new`; `filter.changedSinceBaseline` reflects a persisted pending-resync marker. `measurement` is optional and only refreshed after operations or on an explicit diagnose.
  - `FolderHealthRecord` — the report plus server-derived `stale`, `stalenessMs`, `measurementAgeMs` and `active`.
  - `FolderHealthHistoryEntry { state, reasons, reportedAt }` — bounded transitions, not one row per heartbeat.
  - `FolderSyncPlan { id, hostId, folderId, assignmentId, intervention, authority, maxDeletePercent, summary, changes, configRevision, filterFingerprint, baselineFingerprint, createdAt, expiresAt }` — a reviewed dry-run intent, including the reviewed deletion threshold. `intervention` is `initialize | seed | resync`; `authority` is `remote | local`. With the daemon's `bisync remote local` command shape, the remote is **Path 1** and the local tree is **Path 2**, so `remote` means `--resync-mode path1` and `local` means `--resync-mode path2`.
    **What authority actually decides:** only the winner when the SAME path was modified on both sides. Files that exist on only one side are copied to the other side regardless of authority, and deletions are never implied by it — the plan's change list is the only statement about deletions. `changes` is capped at 20 entries per list, so the counts are exact only up to that cap; a plan reports the samples it has plus the totals it measured.
  - `FolderPlanWithValidity { plan, validity: { valid, reason, message } }` where `reason` is `null | expired | config_changed | filter_changed | baseline_changed | missing`.
  - `FolderInterventionPayload { folderId, intervention, authority?, planId?, confirm?, maxDeletePercent? }` — the complete allowlist for a mutating folder action. `initialize` requires `authority: "remote"`, `seed` requires `authority: "local"`, `resync` requires an explicit `authority` of either side; all three require a reviewed `planId` **and** `confirm: true`. `resume` continues a stopped run and requires `confirm: true` but no plan; `cancel` takes no plan, no authority and no confirmation. A `planId` is rejected for `resume`/`cancel`. Nothing else is accepted.
  - **Execution is bound to the reviewed plan, not to the request.** `checkPlanSemantics` (core) and `verifyPlanAgainstLive` (daemon) compare the requested intervention, side and threshold with the plan's stored values and refuse any mismatch; on success the daemon executes the PLAN's own values. A plan reviewed as "seed from this host at 10%" can therefore never authorize a remote-authority resync or a 90% threshold, and an expired/changed plan is refused as before. The refusal result reads `plan refused — …`.
  - `MAX`/cadence constants: `FOLDER_HEALTH_STALE_MS` (15 min), `FOLDER_PLAN_TTL_MS` (30 min), `FOLDER_HEALTH_HISTORY_LIMIT` (50), `FOLDER_HEALTH_DEEP_INTERVAL_MS` (24 h).
- LAMA-346 initial large-folder seeding contract (shared by daemon, server and web UI, exported from `@lamasync/core/folder-seed`):
  - **A seed plan is never automatic, and its source is never inferred.** `SEED_PLAN_REQUIRES_OPERATOR` is `true` and `POST /folders/:id/seed-plans` requires `confirm: true` **and** `sourceHostId`. The planner only *recommends* a seed above `SEED_RECOMMENDATION_FILE_THRESHOLD` (3,000 entries) and ordinary sync is always still available.
  - **Source authority is explicit and persisted.** `sourceHostId` must be assigned to the folder, must not be the target, and must hold a measurement fresher than `SEED_SOURCE_MEASUREMENT_MAX_AGE_MS` (26 h) with a non-zero entry count. The verdict is stored in `folder_seed_plans.source_authority_host_id` / `source_authority` and exposed as `plan.sourceAuthority { hostId, assignmentId, selectedBy: "operator", assigned, isTarget, measurementUsable, measurementAgeMs, fileCount, totalBytes, measuredAt, message }`. The planner never picks "the largest other assignment".
  - `SeedPlan { id, hostId, sourceHostId, sourceAuthority, folderId, assignmentId, recommendation, source, target, space, filterUniverse, archive, stagingPolicy, configRevision, filterFingerprint, baselineFingerprint, createdAt, expiresAt, execution }` — a read-only preflight. `source` is the named source device's own reported measurement; `target` is the target's own reported free space plus its staging proof; `archive` records the chosen format and whether the target actually reported the tooling to build/unpack it; `execution` is `{ available, reason }`.
  - **The archive is built from the folder's EFFECTIVE FILTER UNIVERSE**, never the raw tree: `SeedSourceFilterUniverse { fingerprint, patterns, includes(relativePath, isDirectory) }` is a required input to the manifest builder, and `filterUniverse { fingerprint, targetFingerprint, match, patternCount, archiveImplemented, message }` records it on the plan. `SEED_FILTER_AWARE_ARCHIVE_IMPLEMENTED` is `true` (Stage 1a, implemented): the daemon compiles the exact `--filter-from` rule lines the executor writes (`lamasyncignore` plus a generated `- .git/**`, with a Git-ignore snapshot prepended when `respectGitignore` is on) into that predicate using rclone's own semantics — first match wins, exactly one space after the sign, **only a trailing-slash rule matches a directory**, a slash-containing pattern is root-relative, `{{...}}` compiles to `^(?:.*/)?<regex>$` — and feeds tar only the manifest's members (`--no-recursion --verbatim-files-from --null --files-from`, NUL-separated) so excluded content can never enter the archive and a legal file name beginning with `-` is treated as a NAME rather than a tar option; a source name tar would escape in its listing (a control character or a backslash) is refused before tar runs. `patternCount` is the source device's countable rule lines (a floor: the Git-ignore snapshot is only built during a run). `match` is false when the target's established baseline used a different filter set, which is refused because that seed would be re-synced afterwards.
  - **Staging policy is a true sibling with a proven filesystem.** `stagingPolicy { adjacentToTarget, derivedSibling, insideTarget, sameFilesystem, message }`: the staging directory must share the target's **direct parent**, be named with `SEED_STAGING_DIR_PREFIX`, be outside the target, and be **proven** by the target device (`facts.seedStaging`) to be on the same filesystem. An unknown verdict is refused, never assumed.
  - **Prerequisites are listed.** `seedPlanPrerequisites(plan)` returns six ordered gates — `source_authority`, `filter_universe`, `staging_same_filesystem`, `target_tooling`, `target_space`, `transport` — each with its own message, so the UI can show every blocker instead of the first.
  - `SeedSpacePlan { sourceBytes, sourceFiles, archiveBytesEstimate, extractedBytes, peakBytes, requiredFreeBytes, targetFreeBytes, shortfallBytes, ok, message }` — peak is `archive + extracted tree` (both exist during extraction), the reservation is `peak × SEED_SPACE_SAFETY_FACTOR (1.25) + SEED_SPACE_FIXED_OVERHEAD_BYTES (64 MiB)`, and `ok` is **false** whenever the target's free space is unknown — it fails closed rather than under-reserving.
  - `SeedArchiveFormat` is `tar.zstd | tar.gz`; `selectSeedArchiveFormat` prefers zstd and falls back to gzip with a documented reason. `isSafeArchiveMember`/`validateArchiveMembers` fail closed on absolute paths, `..`, drive/UNC prefixes, backslashes, NUL/control characters and over-long names.

Smart retention is a preset that expands to visible rules — never stored as an opaque label.
- `RetentionEvaluation { now, timezone, decisions[], keptCount, deleteCount, reclaimableBytes, unknownSizeCount, guardCount, keptByGuarantee }` — pure deterministic evaluation; `reclaimableBytes` sums only known sizes; `decisions[]` = `{ id, action: "keep"|"delete", reason, kind: "guard"|"policy" }`. At least one successful snapshot is always kept; pins/holds + unfinished rollback artifacts override every rule.

- `QueuedAction { id, hostId, type, payload?, status, createdAt, takenAt?, completedAt?, result? }` — action types (LAMA-198/LAMA-299): `trigger_sync`, `trigger_backup`, `check_update`, `refresh_config`, `update_daemon`, plus the **LAMA-345** folder-health trio `diagnose_folder` (read-only), `plan_folder` (read-only dry run) and `folder_intervention` (the only mutating folder action). **LAMA-346 Stage 2d** adds `seed_job` (payload `{ jobId, role: "source"|"target" }`), which runs ONE side of an initial seed. `POST /seed-jobs` enqueues one per party automatically — it is not accepted on `POST /hosts/:hostId/actions`, so an operator cannot hand-craft one. The daemon re-derives its role from the job and refuses a payload that disagrees, and the whole action is inert unless the doubly-gated seed seam is on (otherwise it acks `failed` without loading the relay transport). `update_daemon` takes NO payload (enqueues 400 on any) — the daemon targets the latest release via the release proxy and picks its own asset; it is admin-only and only meaningful for daemons at or above `REMOTE_DAEMON_UPDATE_MIN_VERSION` (0.3.6). LAMA-311: `update_daemon` also reconciles the daemon's systemd **user unit** even when the binary is already current (it removes the obsolete pre-LAMA-311 `ProtectHome=` / `ReadWritePaths=` directives, preserving every other line — custom `ExecStartPre`/`ExecReload`, binary/socket paths, drop-ins and symlinked units are refused with guidance), and it writes **exactly one** terminal ack, *before* requesting the restart; if the ack cannot be written the daemon does **not** restart, so the action stays claimable and is retried. A unit that could not be reconciled (for example the pre-fix sandbox makes `~/.config/systemd/user` read-only for the running daemon) is reported as `failed` with the manual remedy: run `lamasyncd --update` from a shell, then `systemctl --user daemon-reload && systemctl --user restart lamasyncd.service`. In every case `done` ≠ confirmed heartbeat — compare the host's next reported version.
- LAMA-311 (action dispatch): `trigger_sync` / `trigger_backup` re-fetch `/config/:hostId` **once** and re-select when a folder-scoped `folderId` is missing from the cached config, before acking. A `failed` result `folderId=… not assigned to host=…` therefore means the folder was still unassigned after the refresh; a `(config refresh failed; …)` suffix means the refresh itself could not reach the server, so the folder may be assigned once the control plane is reachable.
- LAMA-345 (folder health + intervention). Read `GET /folders/:id/health` for `records[hostId]`: `state` is one of `healthy | new_host | resync_required | recoverable | unsafe | blocked | busy | unknown`, and `reasons[0]` carries the message plus the exact remediation. The workflow is **Diagnose → Plan → Approve → Execute → Verify**:
  1. `POST /hosts/:hostId/actions {"type":"diagnose_folder","payload":{"folderId":"<id>"}}` refreshes the device's facts and deep measurement; the completion `result` starts with the state.
  2. `POST /hosts/:hostId/actions {"type":"plan_folder","payload":{"folderId":"<id>","intervention":"initialize|seed|resync","authority":"remote|local","maxDeletePercent":10}}` runs a real dry run against the device's own bisync workdir (using the assignment's own timeout, not the short ad-hoc preview budget). The change list is read from rclone's machine-readable `skipped` dry-run marker, so `changes.wouldCopy`/`wouldDelete`/`wouldMkdir` and `changes.files`/`changes.bytes` are a real preview; a dry run that does not complete (non-`success`) fails the plan instead of becoming a phantom "0 changes" plan. Wait, then read `GET /folders/:id/plans` and take the newest entry whose `plan.intervention`, `plan.authority` and `plan.maxDeletePercent` match what you asked for. `validity.valid` must be `true`; anything else tells you to plan again.
  3. Approve with `POST /hosts/:hostId/actions {"type":"folder_intervention","payload":{"folderId":"<id>","intervention":"…","authority":"…","planId":"<plan.id>","maxDeletePercent":10,"confirm":true}}`. The `maxDeletePercent` is optional: omitting it means "use the plan's value". Sending a different value is refused rather than silently executed. `initialize` only accepts remote authority, `seed` only local authority. The daemon re-checks the plan against its own config revision, filter fingerprint, listing pair **and reviewed semantics**.
     A plan whose dry run reported no copies, deletes or directory changes is a legitimate **baseline-only recovery** (rebuild a missing/unsafe listing pair when both sides already agree), not a content run. The server accepts it; the daemon then re-runs a fresh dry run with the plan's own reviewed control and refuses the execution if that run reveals any copy, delete or mkdir (release-blocking cachy incident: a stale "0 change" review would have run 349 transfers). Plan again for a content run once the folder state changes.
  4. `intervention: "resume"` continues recoverable work with no resync (and requires `confirm: true`); `intervention: "cancel"` stops an in-flight run and reports the distinct `cancelled` status (never `failed`).
  5. Long plan/intervention actions hold a renewable lease: the daemon renews `POST /actions/:id/lease` every minute while the action is in flight, so a Projects-scale run cannot be reclaimed by the stale-taken sweep and re-executed concurrently. A duplicate claim of an in-flight action is a logged no-op, and a duplicate `POST /actions/:id/complete` cannot rewrite a terminal outcome.
  A completed run is only `success` once the listing pair was verified; a run that left no usable pair fails even at rclone exit 0. `sync now` (`trigger_sync`) is only appropriate when `facts.baseline.ready` is true.
- `ServerDeployJob { id, requestedAt, requestedBy?, status: "pending"|"running"|"succeeded"|"failed", startedAt?, completedAt?, target: "production", summary?, outputTail? }` (LAMA-301) — one active production job max; `outputTail` is the sanitized final 16 KiB of the fixed update script. Only the `LAMASYNC_DEPLOY_AGENT_ENABLED=true` environment accepts new jobs (else 409 “manual deploy only”).
- `LockInfo { folderId, lockedBy, lockedAt, lockTtl }`
- `PauseState { scope: "global"|"host", hostId?, until (ISO), mode: "pause"|"slow", bwlimit? }` — `bwlimit` is a single-segment rclone size (e.g. "1M"); honored only when `mode === "slow"` (LAMA-273)
- `EffectivePause { until (ISO), mode: "pause"|"slow", bwlimit: string|null }` — embedded on the `/config/:hostId` payload as `pause`; resolved server-side as the host row if present, else the global row, else null (LAMA-273)
- `PairingSessionCreateResponse { code, expiresInSeconds }` (LAMA-262)
- `PairingSessionStatusResponse { status: "pending"|"used"|"expired", expiresAt (ISO) }` (LAMA-262)
- `PairingSessionExchangeResponse { apiKey }` (LAMA-262)
- `OperationLogExport { archived, file: string|null, deleted, olderThanMs, targetDir }` — response of `POST /api/v1/admin/export` (P-B cleanup #6). `file` is the absolute path of the `.ndjson.gz` archive on the server; `null` when nothing was archived.

`?`-marked fields are nullable. Timestamps are milliseconds since epoch.

## Operational notes

- The DB file is `<LAMASYNC_DATA_DIR>/lamasync.db`. Don't move or rename
  it while the server is running.
- App snapshot tarballs live under `<LAMASYNC_BACKUP_DIR>/apps/<protectionId>/<timestamp>-<uuid>.tar.gz` (the DB stores the path relative to `LAMASYNC_BACKUP_DIR`).
- `operation_log` retention is `LAMASYNC_LOG_RETENTION_DAYS` (default 90).
  Prune manually via `POST /api/v1/admin/prune?olderThanMs=<ms>` (safety
  rule 5: explicit intent for any destructive API call).
  - **Archived export** (`POST /api/v1/admin/export`) writes every
    operation_log row older than the cutoff to a gzip'd NDJSON file and
    THEN deletes them — preserving the safety-rule invariant that no row
    vanishes before its archive is durable. Body: `{ olderThanMs? (default
    90d), targetDir? (default `LAMASYNC_BACKUP_DIR`, falls back to
    `os.tmpdir()`) }`. Response: `{ archived, file, deleted, olderThanMs,
    targetDir }` — `file` is `null` when nothing was archived so a daily
    timer can re-fire without producing extra files. Archive file name:
    `lamasync-oplog-<unix-epoch-seconds>.ndjson.gz`. Format: one JSON
    object per line in the DB's column order (camelCase keys: `id`,
    `timestamp`, `hostId`, `folderId`, `operation`, `status`, `summary`,
    `details`, `durationMs`, `demo`), rows sorted by `id` ASC so the file
    is replay-friendly. The archive write goes to a `.ndjson.gz.tmp`
    sibling first, is fsync'd, and atomically renamed before the DB
    delete; an interrupted write therefore leaves rows in the DB for the
    next call.
- The `/api/v1/browse/*` write endpoints (copy/move/rename/mkdir/upload/
  delete) all run as async jobs; track via `/api/v1/browse/jobs`.
- LAMA-321: `POST /api/v1/browse/size` is a **read-only** async job for
  ONE folder-relative prefix (`{ ref, prefix }`, where `prefix` is relative
  to `ref.path` and may be nested, e.g. `.Trash/1000`). S3 prefixes are
  measured by paginated ListObjectsV2 (1000 keys/page); local trees by a
  symlink-safe walk. `GET /api/v1/browse/size?kind=s3|local&folderId=…&path=…&prefix=…`
  returns the cached measurement (`BrowsePrefixSizeResult`, 5-minute TTL) —
  a miss means the job is still running or was never started. Directory
  rows of a browse listing show the cached bytes once measured. Failures
  are scrubbed (job error + operation log never contain upstream S3 bodies
  or absolute local paths). "Empty trash" in the web UI is NOT a separate
  endpoint: it deletes the detected trash prefix through the existing
  `POST /browse/delete` job (`names: [".Trash-1000"]` or
  `[".Trash/1000"]`), which carries the same busy guard, audit trail, and
  cache invalidation as any other delete. Every terminal browse job now
  writes `operation_log.trigger = 'manual'`; s3 folder jobs stamp
  `folder_id`, and size/delete jobs whose counts are known include
  `{ prefix, objectCount, bytes }` in `details`.
- LAMA-260 file uploads into synced folders (`POST /api/v1/folders/:id/files`,
  multipart `file` field, optional `path` subdir under the folder's
  destination root). Synchronous, not async; returns
  `FolderFileUploadResponse { ok, name, path, size }` on success. Body is
  streamed to a server-side `/tmp` staging file and `rclone copyto` pushes
  it onto the folder's destination backend:
  - Writable backends only — `s3` (bucket root + subdir), `local`, `nfs`
    (both rclone-type=local against the backend's `localPath`).
  - 409 (not writable) for `sftp` (no per-host credentials available
    server-side — uploads route through the daemon in a separate channel,
    not in scope for LAMA-260) and `restic` (use the snapshot/restore
    flow instead).
  - 404 for unknown folder, 400 for missing `file` field or unsafe path
    (the route reuses `browse-paths.validateBrowseInput` so absolute paths,
    null bytes, and `..` traversal are rejected).
  - Size cap defaults to **100 MB**, env-overridable via
    `LAMASYNC_FOLDER_FILE_MAX_BYTES` (positive integer bytes). The cap is
    enforced mid-stream against `File.size` AND a per-chunk
    `TransformStream` so an oversized body can't slip past a missing
    Content-Length, AND the post-stream `statSync` so the temp file
    can't lie. Anything over the cap returns **413** with the file size
    and the cap in the message; the staging file is removed in a
    `finally` regardless of the cap's verdict.
  - On rclone failure (non-zero exit) the response is **502** with the
    usual LAMA-226 scrubbed summary (`rclone copyto failed with exit
    code <n>`). Full stderr — which can embed bucket, endpoint, and
    access-key fragments — is logged server-side only via `console.error`,
    never echoed back to the client.
  - The staging file lives in `/tmp/lamasync-folder-upload-<uuid>` and
    is `rmSync`'d in the route's `finally` so a crashed handler or a
    cap-rejected body never leaves a partial file behind.
- Pairing flow (LAMA-262):
  - **Create** (`POST /api/v1/pairing`) — admin creates a session with a
    short human code (`LAMA-XXXX-XXXX`). Code alphabet excludes 0/O/1/I/L
    so a fat-fingered code still maps back to the same row. Default TTL
    600s (10 minutes), `ttlSeconds` body field clamps to 30..3600 (1
    minute..1 hour). 201 → `{ code, expiresInSeconds }`.
  - **Status** (`GET /api/v1/pairing/:code`) — admin polls without ever
    revealing the API key. 200 → `{ status, expiresAt }`. 400 on bad
    code shape, 404 on unknown code. Belt-and-braces: every read also
    flips any pending row whose expiry has elapsed to `expired`, so the
    caller observes a current view without waiting for the periodic
    sweep.
  - **Exchange** (`POST /api/v1/pairing/:code/exchange`) — **deliberately
    auth-exempt** (see `auth.ts`'s `AUTH_EXEMPT_ROUTES`): the device has
    no API key yet, so requiring the bearer would be a chicken/egg. The
    code itself is the proof of intent; the body carries the device's
    `{ hostId, hostname }`. Single-use: 200 → `{ apiKey }` on the first
    claim, 409 on any subsequent exchange, 410 on expired. LAMA-234: the
    issued key is a managed DEVICE key bound to `hostId` — never the
    server's `LAMASYNC_API_KEY` — so a compromised device credential is
    containable to that device. The row stays `used` after a failure,
    so retry with a fresh code.
    The `hostname` becomes the key's display name in the Admin UI.
  - Periodic sweep: `LAMASYNC_PAIRING_SWEEP_MS` (default 5 minutes; set
    to `0` to opt out) drops `expired` rows whose `expires_at` is older
    than 24h so the table doesn't grow without bound. The sweep is
    gated by the same `LAMASYNC_TEST=1` env check that keeps the rest
    of the boot-time timers out of unit tests.
- Backup health (LAMA-266):
  - **Prove it** (`POST /api/v1/backends/:backendId/prove`) restores ONE
    random small file from the backend's latest restic snapshot into a
    private `mkdtemp` directory under `os.tmpdir()`, verifies the
    restored file matches the snapshot listing's recorded size + is
    non-empty, and cleans up the tempdir in a `finally`. Never writes to
    a real folder. On failure the response `detail` is a SCRUBBED summary
    (stage + exit code only) — never raw restic stderr, never secrets.
    Backend must be a restic backend with at least one snapshot; otherwise
    the route returns `409 {"error":"prove requires a restic backend with snapshots"}`.
  - **Fire drill** (`POST /api/v1/backends/:backendId/drill`) wraps prove
    with a liveness probe (`restic snapshots --json`) and writes an
    audit row to `operation_log` (host_id = `_backup-health-drill`,
    operation = `backup_drill`) + a `health_drills` row + a notification
    through the existing engine (LAMA-200). The same path runs on a
    monthly cadence inside the server process — see env vars below.
    Backend must be a restic backend; otherwise the route returns
    `409 {"error":"backend is not a restic backend (missing repository or password)"}`.
  - Cadence env vars (both default to a monthly pass + a 1h server-side
    check tick): `LAMASYNC_DRILL_INTERVAL_MS` (per-backend due interval,
    default `30 * 24 * 60 * 60 * 1000`) and `LAMASYNC_DRILL_CHECK_INTERVAL_MS`
    (how often the server looks for due backends, default `60 * 60 * 1000`).
    Set either to `0` to opt out.

## Web app assets (served from the origin root, not `/api/v1`)

Browser plumbing for the installable web app (LAMA-329 phase 7). These carry
no bearer auth and no fleet data — the SPA shell they belong to is already
public at `GET /`. They are routes rather than files because the web UI is
inlined into one `index.html` by `scripts/inline-web-ui.ts`, which also deletes
`dist/assets/`, so there is no static-asset directory to serve from.
