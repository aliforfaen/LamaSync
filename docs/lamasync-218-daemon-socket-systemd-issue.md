# Daemon exits silently under systemd --user due to socket-bind EROFS

## Summary

`lamasyncd` reports itself online to the server and then **exits cleanly within
~1 second** (exit code 0, no signal received, no shutdown log), causing the
host to flip back to OFFLINE on the next heartbeat interval.

The root cause is that the systemd unit template generated by the installer
(`ProtectHome=read-only` + empty/wrong `ReadWritePaths=`) **makes `/run/user`
read-only**, which collides with the daemon's socket path under
`$XDG_RUNTIME_DIR`. The bind returns `EROFS` (`errno 30, syscall=listen`) and
the daemon silently dies because the socket error handler is registered
*after* `server.listen()`, so the synchronous error event becomes an unhandled
'error' that crashes the process with exit 0.

## Reproduction

1. Fresh `lamasyncd` install (v0.2.3) on a Linux host with systemd --user.
2. The installer writes a unit with `ProtectHome=read-only` and
   `ReadWritePaths=%h/.config/lamasync %h/.local/share/lamasync
   %h/.cache/lamasync %h/lamasync.sock` — note the last entry is a **file**
   path, not a directory.
3. Default socket path: `~/lamasync.sock` = `/home/<user>/lamasync.sock`.
4. Run `systemctl --user restart lamasyncd` and watch the journal:

```
lamasyncd[PID]: lamasyncd starting host=... socket=/home/<user>/lamasync.sock
lamasyncd[PID]: [boot] registered and reported online host=... lanIp=...
lamasyncd[PID]: [lock] released 0 stale lock(s)
lamasyncd[PID]: [socket] failed to unlink stale socket /home/<user>/lamasync.sock: EROFS: read-only file system, unlink '/home/<user>/lamasync.sock'
lamasyncd[PID]: [socket] listening at /home/<user>/lamasync.sock
lamasyncd[PID]: lamasyncd ready; cache=... lastHeartbeat=...
lamasyncd[PID]: [socket] listener error: Failed to listen at /home/<user>/lamasync.sock
(daemon exits with status=0/SUCCESS within 1s; no SIGTERM logged)
```

Running the same binary manually outside systemd works fine — bind succeeds,
daemon stays alive. So the issue is purely the systemd environment.

## Minimal reproducer (any Bun script)

```js
import { createServer } from "node:net";
const s = createServer();
s.on("error", (e) => console.log(`FAIL: ${e.code}`));
s.listen("/run/user/1000/lamasync.sock", () => { console.log("OK"); s.close(); });
```

Drop this into a systemd user unit with the installer's hardening
(`NoNewPrivileges=true PrivateTmp=true ProtectSystem=full ProtectHome=read-only
ReadWritePaths=%h/.config/lamasync ...`) and the bind fails with `EROFS`.
Remove `ProtectHome=read-only` and it succeeds.

## Root cause

`ProtectHome=read-only` does **not** just protect `/home`, `/root` — it also
makes `/run/user` read-only (per systemd.exec(5)). The socket default
`~/lamasync.sock` was always meant to live in `$HOME`, and the install script
worked around that by adding `%h/lamasync.sock` to `ReadWritePaths`. But
`ReadWritePaths` matches **directory trees**, not individual files — adding a
file path doesn't actually whitelist the parent directory for writes. So:

- Old code path (~/lamasync.sock): writes hit EROFS from `ProtectHome`,
  masked by the bogus single-file `ReadWritePaths` entry that doesn't
  actually whitelist anything.
- The fact that it ever "worked" was luck: the listen succeeded before
  ProtectHome enforcement kicked in, OR the user's `/home` is on a writable
  filesystem where systemd's read-only bind mount doesn't apply.
- On hardened systems (btrfs subvol, root-on-zfs, etc.) the unlink fails.

A secondary bug: the daemon's new default `$XDG_RUNTIME_DIR/lamasync.sock`
(under `/run/user`) ALSO hits `EROFS` because `ProtectHome=read-only` covers
`/run/user` too — and the template didn't add `/run/user` to `ReadWritePaths`.

A tertiary bug: `socket.ts` registers `server.on("error", ...)` **after**
`server.listen(...)`. If the bind emits an error synchronously (as it does
here), the error event fires before our handler is attached, becomes
unhandled, and crashes the process with exit code 0.

## Fix (already applied + verified locally)

### `packages/daemon/src/socket.ts`
Register the error handler **before** calling `listen()`:

```ts
const server: Server = createServer(...);
server.on("error", (err) => {
  console.error(`[socket] listener error: code=${err.code} errno=${err.errno} syscall=${err.syscall} path=${err.path} msg=${err.message}`);
});
server.listen(opts.socketPath);
```

### `packages/daemon/src/index.ts` (`defaultSocketPath`)
Default to `$XDG_RUNTIME_DIR/lamasync.sock` (always writable under systemd
user services, removed on logout) with `~/.lamasync/lamasync.sock` as the
fallback when `XDG_RUNTIME_DIR` is unset — that subdirectory lives under
`$HOME` cleanly and doesn't pollute `$HOME` itself:

```ts
function defaultSocketPath(): string {
  if (process.env.LAMASYNC_SOCKET_PATH) return process.env.LAMASYNC_SOCKET_PATH;
  const xdg = process.env.XDG_RUNTIME_DIR;
  if (xdg) return join(xdg, "lamasync.sock");
  return join(homedir(), ".lamasync", "lamasync.sock");
}
```

### `packages/daemon/src/systemd.ts` (`DEFAULT_SOCKET_PATH` + `daemonServiceTemplate`)
- `DEFAULT_SOCKET_PATH = "${XDG_RUNTIME_DIR}/lamasync.sock"` (matches the new
  daemon default).
- `ReadWritePaths=` adds `/run/user/%U` so the socket bind succeeds even with
  `ProtectHome=read-only`. Removed the bogus `%h/lamasync.sock` (file path)
  entry that never actually whitelisted anything.

### `packaging/install/install.sh`
Same defaults: `SOCKET_PATH` resolves to `$XDG_RUNTIME_DIR/lamasync.sock`
when available, else `~/.lamasync/lamasync.sock`. ReadWritePaths adds
`%h/.lamasync` (for the fallback) **and** `/run/user/%U` (for the default).
Help text updated.

### `packages/daemon/src/systemd.test.ts`
Updated to assert the new `${XDG_RUNTIME_DIR}/lamasync.sock` default.

## Severity

**High** — fresh installs on hardened systemd hosts ship a daemon that
appears to work (one heartbeat goes through) then dies. Easy to mis-diagnose
as "old config from previous installs" (LAMA-198 dogfood report suspected
this too).
