# LAMA-296 phase 1 — Android shell and QR authentication foundation

Status: implementation specification, 2026-09-06. Owner requested a bounded assignment suitable for a cheaper coding model, with subsequent review by the planning agent. Do not implement the entire Android roadmap in this assignment.

## Assignment and definition of done

Build a sideloadable Kotlin Android app that scans a QR generated by the authenticated desktop web UI, enrolls a new mobile device, and opens the existing web UI with full fleet administration without another login. Independently demonstrate that its native API credential can identify only its own mobile registration and cannot administer the fleet or retrieve desktop backend configuration.

This document's **phase 1 corresponds to stage 0 of docs/handoff-296-android.md**, plus Android scaffolding. It does not mean the broader handoff's stage 1 manual uploads. This narrower scope controls this assignment. Preserve that handoff and its deferred features.

Required delivery: server contracts and migrations, desktop QR flow, session-aware SPA, native app and credential storage, revocation, automated tests, reproducible APK build, and a manual emulator test checklist. Emulator availability is not assumed; the owner is setting one up. Missing instrumentation must be reported as unverified, not replaced with a claim based on mocks.

## Agreed decisions

- Android only; sideloaded APK. Use a standalone `android/` Gradle project to avoid Bun's packages/* workspace discovery. No Play Store work.
- Full administration in the embedded web UI. Native uploader authority stays separate and restricted. The user performs one enrollment, not two logins.
- One enrolled server per app installation for this phase. Re-pairing is explicit and clears previous local auth before activating the new server.
- HTTPS origin with normal certificate validation for real use. Existing HTTP tailnet installations remain supported by existing clients, but the new Android flow requires an HTTPS front door. Document local TLS setup; do not modify production networking.
- App launch/resume check-in only. No background service, upload scheduler, camera/media discovery, storage permissions, upload endpoints, folder creation, or transfer queue in this phase. Camera permission is only for QR scanning.
- No new feature toggles, placeholder upload buttons, speculative queue tables, or capability framework covering every future platform. Optional conveniences from the handoff remain deferred.

## Authentication design — required boundaries

Use distinct native and web authority issued by the trusted enrollment. Do not give the app a general managed admin API key, do not inject bearer keys into JavaScript/storage, and do not let a native device token mint an admin session.

Implement these logical records (names may follow repository conventions):

1. Mobile enrollment: random public ID, hash of a cryptographically random 256-bit QR secret, server-selected new host ID, explicit web-admin grant, expiry, and consumed/revoked state. Ten-minute expiry; server controls grant values.
2. Mobile registration: host ID, client type android, native credential linkage, web-grant linkage, creation/last-seen/revocation metadata. This is one installation, not a user account.
3. Web grant: separate opaque renewal credential, stored hashed server-side, tied to the same registration and its authorized administration grant. It is accepted only by the web-session bootstrap route, never as a normal REST bearer or native identity.
4. Web session: hashed random session secret, registration/grant linkage, issuance/expiry. Use a 12-hour absolute session lifetime; app can obtain a new session using the still-valid web grant without another QR. Native and web grant remain valid until revoked for phase 1. Do not add refresh rotation unless its crash/retry behavior is implemented and tested.

Store native token and web grant encrypted locally using Android Keystore-backed key material; exclude secret files from Android backup/device transfer. Clear them and WebView auth on disconnect. Losing key material requires re-pairing, not plaintext fallback.

A new mobile principal or an explicitly enforced credential subtype is acceptable. It must fail closed throughout REST, WebSocket and config dispatch. Audit the current resolvePrincipal default-admin branch when extending credential kinds: unknown kinds MUST NOT become admins. Auth identity must be request-local; verify concurrent requests cannot share principal state through a mutable Elysia store.

Persist records in both SERVER_SCHEMA and MIGRATIONS. Enrollment consumption, registration, grants, and credential creation must be transactional: concurrent exchanges produce at most one installation; failed issuance does not leave half-issued authority. If a successful response is lost, an already-consumed QR fails safely; desktop can revoke that registration and generate a fresh QR. Do not retain plaintext secrets to replay responses.

## Proposed API surface

Use these route names unless an actual repository collision requires a documented rename. Define request/response types and stable errors before implementing UI.

| Route | Authority and behavior |
| --- | --- |
| POST /api/v1/mobile/enrollments | Existing admin/master or authorized admin web session. Creates new enrollment, returns ID, one-time QR secret, expiry and validated canonical HTTPS origin. |
| GET /api/v1/mobile/enrollments/:id | Admin. Returns pending/used/expired/revoked and paired host metadata, never secrets. |
| POST /api/v1/mobile/enrollments/:id/exchange | Exact unauthenticated route; enrollment ID + secret in JSON body and display name/app version. Returns server-created host ID, native token and separate web grant once. Client may not choose an existing host ID or grant level. |
| POST /api/v1/mobile/web-session | Exact bootstrap route authenticated by web grant in JSON body; issues cookie to the HTTP client. Accept no cross-origin browser request. Native token alone receives 403. |
| GET /api/v1/mobile/me | Mobile native principal; returns own host ID, display name, client type/version and revocation-safe minimal metadata. No backend config, secrets, fleet data or pretend upload capabilities. |
| POST /api/v1/mobile/check-in | Mobile native principal; updates own last seen/app version. Host identity comes from principal, not submitted hostId. |
| POST /api/v1/mobile/registrations/:hostId/revoke | Admin. Revokes native access, web grant, and all web sessions for registration atomically; repeat calls are safe. |
| POST /api/v1/mobile/web-session/logout | Current web session with CSRF protection. Invalidates that session and clears cookie. Does not implicitly revoke the native registration. |

Use 400 for invalid shape/origin, 401 for absent/invalid/revoked authority, 403 for valid authority without required permission, 409 for consumed enrollment, 410 for expired enrollment, and 429 for throttling. Bound payload lengths. No secrets in errors. Add exact method/path exemptions, not a broad /mobile auth bypass.

Apply bounded exchange rate limiting before expensive work (initial policy: 10 attempts/minute per trusted client address plus 5 attempts/minute per enrollment ID; expire limiter entries). Do not trust arbitrary X-Forwarded-For. Document proxy assumptions; test limits without sleeping. Enrollment status polling stops at terminal state, with a modest interval rather than a tight loop.

## Cookie and SPA integration

Use a host-only `__Host-lamasync-mobile` cookie with Secure, HttpOnly, SameSite=Strict and Path=/. No Domain attribute. Native bootstrap uses its HTTP client, transfers only that cookie into Android CookieManager for the exact enrolled origin, waits for completion, then loads the SPA. Do not copy the native token or web grant into the cookie. Do not put session secrets into URLs. Reject cross-origin redirects during credential exchange/bootstrap.

Add explicit bearer and web-session modes to the SPA auth abstraction. Session mode discovers auth through /auth/me; no dummy key in sessionStorage to fool App.tsx. Existing browser bearer login remains compatible. When an Authorization header is present but invalid, fail rather than falling back silently to cookies. Session resolution maps to admin permissions while retaining registration/session provenance for revocation and auditing.

Cookie-authenticated mutations require a session-bound CSRF token and exact trusted Origin validation. Deliver the CSRF token through authenticated auth metadata; it is not a bearer credential. Audit multipart and download helpers as well as normal fetches. Do not apply cookie-specific CSRF requirements to existing native bearer clients. Bootstrap may accept missing Origin for native requests, but if Origin is present it must match the configured canonical origin. Use configured origin, not untrusted forwarding/Host headers, as the trust anchor.

WebSocket cookie upgrades require exact Origin and a live session; preserve existing bearer subprotocol support. Closing/revoking a mobile session must disconnect its existing subscription immediately in-process. Session expiry must also close/stop delivery to active connections. Restarted server revalidates stored session/registration state. Clearing only a cookie or rejecting only new requests is insufficient.

No JavaScript-to-native credential bridge is needed in this phase. A native “Reconnect web session” action can re-bootstrap when the web session expires, without asking for keys. Web logout should remain logged out until the user explicitly reconnects; avoid immediately recreating a session in a logout loop.

## Desktop and native UI

Desktop: retain CLI pairing; add Android enrollment with clear text that it grants full web administration and separate native identity. QR payload is versioned JSON: `{ "kind": "lamasync.android.enroll", "version": 1, "serverOrigin": "https://…", "enrollmentId": "…", "secret": "…" }`. Display expiry/status and regeneration. Regeneration invalidates any still-pending previous enrollment. Provide a registration revoke action and visible paired device identity.

Native screens: Scan QR; server/name confirmation; enrollment progress; management WebView; simple native connection panel showing server, own device ID/name, version, check-in result, Reconnect web session, and Disconnect. Disconnect attempts server-side revocation through an authorized web session (bootstrap it with the separate web grant if necessary, then satisfy session CSRF rules), then clears local data even if offline; explicitly explain when remote revocation could not be completed and can be done from desktop. Never grant native uploader credentials general revoke/admin authority.

Validate QR kind/version, HTTPS origin, no username/password/query/fragment/path other than root, bounded fields, and expiry errors. Use a maintained scanner library with an explicit version; choose current compatible stable Android tooling and record JDK/SDK/Gradle requirements. Application ID must stay stable once chosen. Minimum SDK 26 is a reasonable project default; document any necessary change.

WebView: allow top-level navigation only to exact enrolled origin; external HTTPS links open externally without app credentials. Reject unsafe schemes and SSL errors. Disable file access, mixed content and release debugging. Enable JavaScript only as required by the SPA. Do not intercept every request to inject native authorization. No global cleartext exceptions. A debug-only trusted local CA setup is acceptable; release must use normal trust validation.

Future seam: a native API client owns only the native token, separate from web-session broker/secret access. This separation is testable now. Do not build upload scheduling or destination grants yet: phase-1 native scope intentionally has no file access, and phase 2 will add explicit destination grants before accepting files.

Required automated evidence:

- Enrollment expired/replayed/malformed/invalid-secret/throttled/concurrent; rollback on issuance error; cannot claim an existing device.
- Native token denied fleet admin, desktop config, key reveal, arbitrary host access and web bootstrap; web grant denied normal REST and native identity.
- Cookie admin session works for REST including multipart/download auth; missing/wrong CSRF or Origin rejected; invalid bearer cannot fall through; credentials/principals isolated under concurrent requests.
- Revocation invalidates all three forms of authority and existing WebSockets; expiry stops live delivery; legacy CLI pairing and bearer WebSocket still work.
- Fresh DB plus migration, no plaintext server-side grant/session secrets; response/list/log redaction.
- QR payload retains case; legacy QR remains unchanged; SPA session detection and logout/reconnect behavior.
- Native unit tests for QR/origin validation, credential-role separation, enrollment errors, stored-state recovery and navigation policy. Instrumented test skeletons must test real app behavior, not just mirror parser tests.
